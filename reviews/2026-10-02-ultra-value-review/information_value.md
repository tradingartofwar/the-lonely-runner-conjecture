## Verdict

The record supports **reusable exact counterexamples and inspectable verification**, not improved AI memory or a distinctive general information calculus. The most useful export now is a small executable lesson/conformance fixture showing when an apparently rich summary cannot answer a changed question. A source-bound decision adapter is a plausible engineering application only if an actual consumer needs to combine the repository's separately checked artifacts. Most of its proposed mechanisms are ordinary keys, types, explicit queries, and existing exact verifiers. That is an acceptable implementation, not a deficiency to disguise with CC terminology.

The two handoff studies should close their respective comparisons. The pilot obtained 40/40 correct requested outputs in both arms; strict full-answer scores were 38/40 versus 37/40, entirely sensitive to five unsupported “another policy” phrases. Run02 obtained CC 17/18, conventional 18/18, and full-source 18/18 supported complete answers. All 36 handoff/query retention checks were adequate, and no reader requested recovery. Its one clear CC error attached destination-audit uncertainty to the known contents of a fixed backup. Neither study establishes a robust CC benefit. Neither the pilot's wording issue nor run02's recipient error warrants relabelling the same comparison as an evidence, memory, or compatibility benchmark.

There is positive value in making failures inspectable. A person can ask a precise question, obtain an exact witness or a counterexample, challenge a representation, and recover the source without having to trust the assistant's confidence. AI can help implement those checks and maintain continuity; the person retains direction, interpretation, and judgment about relevance. This expands the practical capacity to participate in technical inquiry. It does not establish superior human–AI reasoning, better learning, better memory, or a solved external operational problem.

## What the physical evidence actually contributes

The September 30 information review correctly recovered the September 27 physical collision. For common-start speeds `{0,1,3,4,5,10,28,y}`, reference 0, threshold `1/8`, and closed window `J=[9/32,3/8]`, the two inputs `y=1680` and `y=3360` have identical all-order joint blocking durations and all 21 gcds among nonzero speeds. Yet their complete local safe sets are `{9/32}` and empty. Both have zero clear duration, and both have a strict safe witness outside J at `11/64`.

This is a particularly useful adequacy counterexample because it is physically realizable, exact, and consequential for a declared query. It is not merely a failure of pairwise information: all 128 subset moments of the seven moving runners agree. Inclusion–exclusion still answers total duration exactly; it cannot distinguish the zero-measure contact. A counterexample to determinacy requires only this pair, not an exhaustive search. In contrast, failure to find such a pair in a finite sample cannot establish determinacy throughout an unbounded class.

Keep three limits visible. The input speeds, reduced ratios, and trajectories are not identical; the summary intentionally omits distinctions in them. The result concerns local existence, not failure of Lonely Runner or different global existence. Finally, the earlier fixed `(6,7,3,y)` blocker family has a control where the reduced denominator of one exact duration identifies endpoint survival. Therefore “all aggregation loses the answer” would be a false lesson. Exact identifiability and stable inference at finite precision are also different: the note has a separate near-collision family whose moment differences tend to zero.

The latest interval study adds a directly usable output-contract distinction. It reports complete physical safe-set equality on 1,197 finite inputs, whereas an individual stored time would certify only one witness. The positive-width policy loses `(1,4,13)`, whose complete `1/8` safe set is four isolated times. The sheet study's source-class failure at `(1,2,40)` is compatible with the physical witness `25/152`. “No retained sheet works,” “this time is safe,” and “this is every safe time” are different predicates over related artifacts. An exporter must preserve that difference.

## The conventional account is already strong

For a declared source class D, retained view V, and requested query Q, the adequacy condition is

`V(d1) = V(d2) implies Q(d1) = Q(d2), for all d1,d2 in D`.

That is established query determinacy, not a new principle inferred from runners. Nash, Segoufin, and Vianu also separate information sufficiency from effective rewriting in a chosen query language. Here the runner example supplies a concrete countermodel to a particular proposed view. No present-day open database problem is claimed solved.

Different established mechanisms handle different obligations:

| Obligation | Adequate conventional mechanism | What it does not establish |
| --- | --- | --- |
| Evidence rows refer to the same object/version/operation | Explicit identity model, composite keys, non-null fields, foreign keys, and an explicit join | Truth of an asserted observation, correctness of extraction, or sufficiency for an arbitrary query |
| An answer records which rows jointly support it and which are alternatives | Database provenance; ordinary derivation records | That source assertions are true; positive provenance alone does not define absence, revocation, or contradiction |
| A history has coherent entity/activity relationships | PROV modeling and applicable consistency constraints | Historical authenticity or semantic entailment of attached prose |
| A certificate belongs to particular bytes and a particular predicate type | Content digest and typed attestation, exemplified by in-toto Statement v1 | That its predicate is true or that its verifier is trusted |
| A mathematical witness satisfies this exact problem | Exact arithmetic over raw speeds, reference, threshold, window, and recovered physical time | Complete coverage or an infinite theorem |
| The retained evidence answers this changed query | A proved rewriting, exact domain-specific argument, or exhaustive check over an explicitly finite source class | Adequacy outside the declared class |

Primary and foreign keys are neither trivial nor sufficient for every row of this table. They handle identity/reference requirements once those requirements are modeled. SQL plus ordinary functions can also implement the decision predicates and finite countermodel search. Thus a checker can do more than *keys alone* without doing anything beyond mature conventional database/programming methods. Compare against that complete baseline, not a deliberately careless join.

Unknown identity must remain unknown: existential evidence for a covering policy does not imply one different from P. Likewise, two labels can name one object, and uncertainty about an operation on one object does not infect a fixed fact about another. These are useful regression rules from the handoff studies. Automatically extracting them from free text is a separate unsolved implementation obligation here; a manually curated typed record does not demonstrate that extraction or AI memory has improved.

## Would a tiny decision checker help?

**Possibly as an adapter, but no missing checker has yet been demonstrated.** The current sheet and orbit verifiers already validate manifests, input lists, source geometry, selected contacts, and exact witnesses. The orbit verifier additionally compares every recovered union with the full physical safe set. Its verification report binds the result bytes by SHA-256 and states its limits. Repeating those checks under a new name adds no mathematical or reproducibility evidence.

A meaningful requirement is narrower: a downstream report, visual, or API wants to combine verified artifacts and emit one machine-readable claim. It must refuse to promote evidence for one source class, input, threshold, or output kind into a different claim. The existing per-study verifiers are the ground-truth computational components; an adapter carries their declared obligations across the interface.

The smallest useful contract would contain the input manifest and artifact digests; verifier revision; physical input/reference/threshold/window/boundary convention; predicate kind (`witness`, `complete_safe_set`, or `finite_case_coverage`); explicit finite domain where relevant; verification outcome; and dependency rows actually used. Its decision output would be `supported_within_scope`, `contradicted_by_checked_evidence`, `insufficient_or_unavailable`, or `invalid_record`. A missing verification is not a mathematical failure; successful byte reproduction is not independent proof review; an unchanged filename is not an unchanged object.

A digest is an integrity check against a trusted pin, not a proof of authenticity or correctness. Neither PROV consistency nor a valid typed envelope can substitute for the physical verifier. Any alleged time saving must include schema authoring, manual extraction, recovery, and maintaining adapters. Without an actual consumer and an observed integration gap, the prudent implementation decision is to retain the existing scripts and source-linked reports.

## At most two bounded next artifacts

### 1. Recommended now: executable query-adequacy lesson/conformance fixture

**Purpose:** make the exact distinction between answering a query and possessing enough information for it reproducible by a reader. This is an artifact extraction, not a third handoff study and not an AI-memory product.

**Small deliverable:** one short lesson and one ordinary Python/SQLite command that imports the pinned contact archive, runs or invokes its two existing exact checkers, and emits the matched moment vectors, both source identities, the two local existence answers, and the distinguishing endpoint certificate. Include the duration query as a sufficient-view control and the original-family denominator example as a warning against overgeneralization. Do not build a general query language or automatic theorem prover.

For an explicitly enumerated source class, the conventional reference implementation groups by the complete retained view and counts distinct query answers. For example, with non-null canonical exact values and one row per admissible source, this diagnostic is ordinary SQL:

```sql
SELECT view_value
FROM admissible_sources
GROUP BY view_value
HAVING COUNT(DISTINCT query_answer) > 1;
```

The artifact must return the two source rows, not only the group or a digest. Canonical strings must be generated from exact reduced rationals and a pinned label order; a rounded or unlabeled view changes the problem. A pair certifies non-determinacy in any declared class containing it. An empty query result certifies only absence of a collision in the exhaustively supplied finite table. For evidence conditioned on a particular view value, zero matching source rows is inconsistency or unavailable modeling, never vacuous success.

**Failure oracle and acceptance:** the existing independently structured contact checks must agree; the moment equality must be componentwise exact; local allowed sets and the outside-J witness must reproduce; the output must distinguish duration, local existence, global existence, and precision. A second reader should be able to recover each displayed claim from the command and cited source. No claim of educational effectiveness follows from this acceptance check.

**Bound and stop rule:** one artifact, the two physical configurations plus the two named controls, no new speed search and no participant collection. Stop if the wrapper merely duplicates the existing lesson/visual with no requested audience or consumption format; in that case add a concise pointer and the SQL analogy to the existing material. If later teaching effectiveness matters, compare with an equal-time simple relational example in a separately designed human study; do not count this artifact or another AI ceiling test as that evidence.

### 2. Conditional: a source-bound claim-export adapter, tested against conventional code

**Entry gate:** identify one actual repository consumer that reads independently produced certificate/verification artifacts and one concrete requested decision it cannot already obtain safely. Write down its exact current read path. If there is no such consumer or unresolved interface, do not start.

**Frozen scope:** support only `one physical witness` and `complete safe set` for a stated finite input, with the current sheet/orbit packages as development material. Use at most 30 predeclared fixtures: 12 valid controls and 18 single-field/interface corruptions chosen before execution. Corruptions should cover wrong artifact digest, result/verifier mismatch, wrong reference/threshold/window, stale input, wrong predicate promotion, and loss of an isolated component. Include a case where every individual supplied file passes its own local validation but the proposed cross-file claim is unsupported. Keep missing evidence distinct from rejected evidence. These deliberate corruptions are fault-injection controls, not frequencies of real-world incidents.

**Strong baselines:** (A) existing per-study verifiers plus an ordinary typed Python adapter; (B) a relational schema with composite keys, `NOT NULL`, explicit output-kind predicates, the same verifier calls, and the same input contract. PostgreSQL `CHECK` alone is not a sufficient missingness guard because null can satisfy it. Both baselines receive exactly the same metadata and truth oracle. A CC-inspired wrapper must earn its extra maintenance cost; it is free to disappear into A or B.

**Oracle:** exact physical phase evaluation decides witness validity; the existing complete interval intersection decides full-set equality. Deterministic envelope comparisons decide identity/type mismatch. Claimed entailment is evaluated against the requested predicate, not a prose grade. A valid witness can pass `witness` and simultaneously be insufficient for `complete_safe_set`. “No sheet contact” cannot certify an empty physical set.

**Success and stop rule:** zero unsupported approvals and zero refusal of valid in-scope controls are required of every implementation. Report the full discrepancy list, total adapter/verification/recovery work, and implementation size. Continue only if the actual consumer uses the export and it closes a predeclared integration gap at acceptable maintenance cost. If ordinary typed code or SQL matches the contract wrapper with no greater burden, adopt that implementation and end the separate CC software claim. If all benefit is hash checking or a same-key join already done by the current scripts, stop after documenting the duplication. Do not add harder fixtures after seeing a tie and call them fresh evidence.
