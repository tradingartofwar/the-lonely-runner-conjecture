# Harbor archive migration

This is a synthetic data-migration history with a closed set of recorded changes. The cutoff is the end of Day 12. The incoming coordinator must decide whether the source may be retired under the supplied data-retention rule, explain the evidence supporting that decision, and assess a small proposed audit completion. File labels are not necessarily distinct stored copies. An ingestion acknowledgment is not a checksum audit. The fictional retirement rule below is the entire decision rule for this exercise; there are no hidden legal, business, or hardware requirements. All records needed for the stated finite questions appear in the chronology.

## H01 — Day 1, retirement rule

The live source may be retired only after the destination is verified to contain every current source key at its current content revision. Ingestion means a destination process accepted a key for writing. Verification means a later audit compared stored destination content to the specified source revision and found a match. The retirement test must include changes made after a snapshot. The coordinator may delay retirement even when a snapshot is mostly verified. A source backup can be useful for recovery but does not by itself satisfy the destination-verification rule.

## H02 — Day 2, snapshot

Snapshot M0 records keys K1 through K96, each at revision 1. There are exactly ninety-six keys at that moment. Its manifest describes that fixed snapshot, not every future source state. The source remains writable during migration. A later key or revision therefore has to be accounted for separately unless a subsequent manifest explicitly includes it. The team records M0's immutable content identifier as object-amber. This name is an identifier within the exercise and carries no claim about a real storage provider or content-addressing implementation.

## H03 — Day 3, two labels

The inventory shows labels backup-east and archive-copy. The storage administrator confirms that both labels resolve to the same single stored object, object-amber, containing M0. Creating archive-copy created an alias, not another independently stored copy. The two labels may be useful to different workflow screens, but the count of physically separate stored objects established by this record is one. Neither label refers to the live writable source or the destination. This identity relation remains unchanged through the cutoff and should survive any abbreviated migration summary.

## H04 — Day 4, ingestion

The destination ingestion service acknowledges all ninety-six M0 keys. Its response says accepted for writing. The response does not report a later readback or checksum comparison. A dashboard marks the transfer batch complete because all input messages have been accepted. The coordinator notes that this is the service's transport-stage completion, not the project's retirement-stage completion. The team keeps both terms because they describe useful but different operations. A handoff that reports only complete would leave the incoming coordinator unable to identify which operation has actually finished.

## H05 — Day 5, audit begins

The destination audit verifies K1 through K60 at revision 1 against M0. All sixty match. A network interruption ends that audit session before the remaining keys are compared. The interruption does not establish corruption in the unaudited keys. It leaves their stored content unverified by this audit. The accepted ingestion record still covers all ninety-six M0 keys, while verified matches currently cover only sixty. These are overlapping stages, not alternative totals that can be added to obtain a larger number of migrated keys.

## H06 — Day 6, audit continuation

The resumed audit verifies K61 through K94 at revision 1 and finds all thirty-four match M0. K95 and K96 are not audited before the session ends. There are now ninety-four verified M0 matches and two unaudited M0 keys, with zero observed mismatches in that audit. The team requests another session for the final two comparisons. This request is not completion evidence. No audit result for either K95 or K96 appears later in the actual history before the cutoff.

## H07 — Day 7, optimistic note

A progress message says the copy looks good and that the ninety-six-key batch is complete. Its linked source is the ingestion acknowledgment. The coordinator annotates the message to preserve that stage and points to the separate ninety-four-key verification record. The message adds no stored-content comparisons. The team does not claim the remaining two keys are corrupt. The correct uncertainty is that their content has not yet been checked. A cosmetic report update groups both records under migration, but their underlying event identifiers remain available.

## H08 — Day 8, first source change

The writable source receives new key K97 at revision 1 after M0. This key is not part of object-amber and was not in the acknowledged M0 ingestion batch. There is no destination ingestion or verification event for K97 anywhere in the supplied history. The project maintains a delta ledger so the snapshot's fixed coverage is not confused with current-source coverage. A plan to perform another synchronization pass is entered, but its execution has not occurred. The source now contains ninety-seven keys.

## H09 — Day 9, second source change

The source content for K12 is updated from revision 1 to revision 2. Its earlier destination verification covered revision 1, which remains an accurate historical result but no longer proves equality with the current source revision. There is no destination ingestion or verification event for K12 revision 2 before the cutoff. All other existing source keys retain revision 1. The delta ledger now contains exactly the K97 addition and the K12 revision change. The ledger is complete for post-M0 changes in this scenario.

## H10 — Day 10, routing discussion

A read-only preview application is pointed at the destination to inspect interface behavior. This routing change does not verify additional contents and does not retire the source. The preview uses a small sample that excludes K95, K96, K97, and K12. Its successful opening therefore cannot fill those evidence gaps. The project lead asks that the successor be able to separate application routing, snapshot ingestion, content verification, and source retirement. Each is a recorded operation with different evidence requirements under this project's supplied rule.

## H11 — Day 11, proposed completion

The team plans to finish the two M0 audit comparisons first, then synchronize the delta ledger and verify the resulting current revisions. These are distinct proposed steps. Finishing the old snapshot audit alone would establish M0 coverage but would not include changes absent from M0. The order is chosen for operational convenience; it is not a proof that the first step satisfies the whole retirement condition. Neither step completes before the cutoff. The source remains available and writable, with no additional recorded changes after Day 9.

## H12 — Day 12, cutoff

The actual destination evidence remains ninety-six ingestion acknowledgments and ninety-four verified M0 matches, with two M0 keys unaudited. The current source has ninety-seven keys, including K97 revision 1 and K12 revision 2. The delta ledger is still unsynchronized. The two backup labels still refer to one object containing M0. This history is complete for source changes, destination ingestion, and audits at the cutoff. Absence of a verification record should be described as missing evidence, not converted into an observed mismatch or an invented successful comparison.
