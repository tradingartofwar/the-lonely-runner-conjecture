# Juniper annotation evaluation

This is a synthetic evaluation history, not a claim about a real model or dataset. The cutoff is the end of Day 12. The incoming evaluator must report the fixed candidate's validation status, explain denominators, and assess whether a later candidate can inherit earlier evidence. The source catalogue is complete. Case identifiers and candidate versions matter. A displayed success percentage is meaningful only with its inclusion rule. There are no statistical inference requirements in this scenario: the acceptance rule is a finite rule supplied below. Descriptions of proposed reruns and prototype repairs are separate from completed evaluations of the selected candidate.

## J01 — Day 1, planned catalogue

The project begins with fourteen registered images: X1, X2, A1 through A8, and B1 through B4. Before either candidate is evaluated, X1 and X2 are found to be unreadable source files. A signed prespecified exclusion rule removes those two cases before outcome inspection. The validation cohort therefore consists of twelve cases, A1 through A8 and B1 through B4. Neither future failure nor difficult appearance is an exclusion reason. The original fourteen-file inventory remains available for accounting, but it is not the acceptance denominator after these authorized exclusions.

## J02 — Day 2, acceptance rule

A candidate passes only if all twelve cohort cases have been evaluated for that exact candidate version and at least ninety percent of the twelve pass. With twelve cases, this means at least eleven passes and no untested case. A failure is an observed incorrect annotation, while an untested case has no outcome. The project forbids substituting another candidate's outcome into a fixed candidate's report. Candidates may share code, but that does not make their validation evidence interchangeable. A future evaluation could establish a changed candidate's result separately.

## J03 — Day 3, first A cases

The selected candidate is C1. Its evaluations on A1, A2, A3, and A4 all pass. The dashboard initially shows four passes from four displayed outcomes. This is a correct description of the then-completed subset. The coordinator asks that the planned twelve-case denominator remain visible beside it, because the screen will be used during a handover before all work is complete. A proposed presentation slide says the system is accurate on the initial examples. That qualitative slide does not establish the final finite acceptance condition.

## J04 — Day 4, remaining A cases

C1 passes A5, A6, and A7 but fails A8. The A8 source image is readable and belongs to the authorized cohort. Its observed failure is not a data-quality exclusion. The complete C1 outcome for group A is seven passes and one failure across eight evaluated cases. The team files a defect for the A8 annotation behavior. The defect's existence does not itself change C1, and no corrected C1 run of A8 appears later. The original failing result remains part of the selected candidate's evaluation.

## J05 — Day 5, B cases

C1 passes B1 and B2 and fails B3. The test process stops before B4 is evaluated because the reserved machine slot ends. B4 remains untested; it is not a failure, an exclusion, or a successful case. The complete C1 outcome for group B is two passes, one failure, and one untested case. No other B outcomes exist before the cutoff. The incoming evaluator is asked to retain the distinction between a stopped collection and an observed bad annotation, even though either can prevent the finite acceptance rule from being satisfied.

## J06 — Day 6, success-only export

A presentation export filters the dashboard to successful outcomes and displays nine passes from nine rows. This filtered table is useful for selecting illustrations of correct annotations. It is not the full cohort report. It hides the two observed failures and the untested case rather than resolving them. The export's heading says selected successful examples; a later thumbnail removes that heading to save space. The preserved full record remains authoritative for candidate validation. The filtered percentage does not supersede case-level outcomes or the prespecified acceptance denominator.

## J07 — Day 7, prototype work

A development branch named C2 changes the annotation routine implicated in B3. The code change is real, but the change alone supplies no new validation outcome. C1 remains the selected candidate throughout the current evaluation. The team may later choose C2 for a separate evaluation, but no decision has been made to replace C1 in the acceptance record. The defect discussion also mentions A8 as a possible future repair target without recording a repair or a new result for that case on either version.

## J08 — Day 8, C2 rerun

C2 is evaluated on B3 and passes. This is the only evaluated cohort case for C2 in the supplied history. Its outcome is linked to C2, B3, and this date. It does not erase C1's B3 failure. A combined development screen can show both rows because they describe different candidate evaluations. Calling the new row a rerun means the same image was used again; it does not mean the earlier candidate was retested. No cross-version equivalence guarantee is available in this fictional project.

## J09 — Day 9, denominator discussion

The coordinator asks for two descriptive fractions for C1 if someone reports a pass rate: passing cases among evaluated cohort cases, and passing cases among all twelve authorized cohort cases. Untested B4 belongs only in the second denominator. The original fourteen-file inventory can be reported separately with its two prior exclusions. These fractions answer different questions. A single percentage without its denominator can obscure both the untested case and the pre-evaluation exclusions. Acceptance still uses the complete twelve-case rule and requires every case to be evaluated.

## J10 — Day 10, no collection resumed

The team requests another machine slot for B4, but the slot is not confirmed before the cutoff. No additional C1 or C2 case is evaluated. The development screen retains C2's successful B3 row alongside C1's earlier results. The project lead wants the handoff to explain which result belongs to which candidate, so an incoming evaluator does not accidentally build a composite candidate that has never been tested. The team also changes the report's color palette; this is a presentation change only and cannot affect any validation count.

## J11 — Day 11, task for successor

The incoming evaluator should be able to answer whether C1 passes today, what the observed and untested counts are, and what would remain to test if the project selected C2 tomorrow. A switch of selected candidate does not retroactively run its missing cases. The prespecified exclusions apply to both candidates because they concern unreadable source files identified before evaluation. Every other cohort case remains eligible for testing. There is no authorization to drop A8 or B3 merely because an earlier candidate found those cases difficult.

## J12 — Day 12, cutoff

The selected candidate remains C1. Its complete group results are those in J04 and J05; its earlier individual passes agree with those totals. C2 has exactly one evaluated cohort case, B3, and that result is a pass. Both X cases remain prespecified exclusions. There are no further runs or changed acceptance rules. The history retains the filtered nine-row presentation export as a separate artifact, so its apparent perfection can be explained without contradicting the full validation record or inventing new evaluations.
