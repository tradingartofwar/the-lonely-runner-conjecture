# Canal telemetry replay

This is a synthetic telemetry investigation with a complete finite event catalogue. The cutoff is the end of Day 12. The incoming analyst must determine delivery performance, recover timings from the appropriate clock, and explain what a changed timing uncertainty would permit. All arithmetic uses seconds on a fictional reference timeline. The task concerns three unique acquired samples, S, T, and U. Transport retries do not create new acquired samples. Clock labels are part of the evidence; numbers copied from different clocks cannot be subtracted until their relation is applied. All intervals and acceptance thresholds in this history include their endpoints.

## C01 — Day 1, definition

A sample passes the delivery requirement if its true gateway arrival time minus its acquisition time is at most two seconds. Acquisition timestamps are already on the reference clock. Gateway timestamps use a different clock. The word delivery in this requirement means arrival at the gateway, not later insertion into a reporting database. Acquisition identifiers remain unchanged when a packet is retried. Every sample in the catalogue must be counted once. The analyst is asked to preserve enough detail to explain both a pass rate and a disputed individual sample.

## C02 — Day 2, dashboard draft

The first dashboard simply subtracts acquisition timestamps from the gateway's recorded timestamp. It labels differences above two seconds as late. The designer acknowledges that this is a provisional display awaiting clock calibration. It is useful for locating rows but is not yet an accepted lateness calculation. A separate graph shows database insertion times, which are intended for checking report backlog. Its title is shortened to receipt time in an early screenshot. The investigation retains that screenshot as historical context rather than silently treating the graph's title as a measurement definition.

## C03 — Day 3, sample S

Sample S is acquired at reference time 100 and has gateway recorded arrival timestamp 104. Its database insertion occurs at reference time 111. The row is intact, and no part of its payload is missing. The transport monitor marks it delivered because an arrival occurred; that mark does not itself decide whether the two-second latency requirement was met. The operator copies both timestamps into the investigation record. S is never retried, and there are no other observations with its acquisition identifier in the complete supplied catalogue.

## C04 — Day 4, sample T

Sample T is acquired at reference time 100.5 and has gateway recorded arrival timestamp 104.5. Its database insertion occurs at reference time 111, the same insertion time shown for S because the reporting process writes them together. The insertion batch therefore does not imply simultaneous acquisition or simultaneous arrival. The packet carries a different acquisition identifier from S and is a distinct sample. There is no retry for T. A chart that groups events by whole database insertion seconds is retained for backlog planning only.

## C05 — Day 5, sample U

Sample U is acquired at reference time 102 and has gateway recorded arrival timestamp 108. Its database insertion occurs at reference time 113. A retry envelope is later named U-retry, but it contains the same acquisition identifier and payload as U. It does not contain a new acquisition or a second first-arrival observation. The packet-level transport log counts this envelope as a second transmission. The sample-level service requirement counts only U once. The investigation must keep those denominators distinct when it translates the dashboard into a readiness report.

## C06 — Day 6, provisional count

An uncorrected screenshot shows four late rows: S, T, U, and U-retry. This is a faithful picture of what the provisional software displayed, not a verified statement that four unique samples violated the service requirement. One issue is clock calibration and another is retry identity. The analyst retains the screenshot to explain why the initial alarm was larger than the eventual sample catalogue. The number four should not disappear from the project history, but its meaning must not change from displayed rows to confirmed distinct failures.

## C07 — Day 7, clock calibration

The timing test establishes that the gateway clock was exactly three seconds ahead of the reference clock throughout all three arrivals. Thus a gateway reading g corresponds to reference time g minus three. The calibration covers the complete relevant arrival period; no drift or additional uncertainty applies in the current case. Acquisition timestamps need no correction. Database insertion timestamps also already use the reference clock. A technician's older guess of a one-second offset is withdrawn. This accepted calibration replaces that guess and governs the current performance calculation.

## C08 — Day 8, identity audit

The complete acquired-sample set is confirmed as S, T, and U. U-retry is an alias for U's retry envelope, not a fourth sample. No hidden samples are omitted, and no original acquisition has been excluded as invalid. Both envelope identifiers remain useful for tracing transport traffic. The service-level report, however, must use the three unique acquisition identifiers. The audit also confirms that the first gateway arrival values recorded in C03 through C05 are the ones to use, rather than the time a retry receipt was copied into the dashboard.

## C09 — Day 9, display repair

The developer plans two independent fixes: apply the accepted clock conversion and group transmissions by acquisition identifier. A preview changes the graph colors and rearranges the sample labels, but it does not add new measurements. The release ticket is still open, so screenshots from the deployed dashboard can continue to show the old provisional counts. The analyst can nevertheless calculate the required results from the preserved raw rows and calibration. A future display update is not a prerequisite for arithmetic, and a display preview is not an extra source of timing evidence.

## C10 — Day 10, contingency convention

The team records how to handle a future uncertainty interval for the offset. If the gateway is ahead by any amount o in a specified closed interval, an arrival reading g corresponds to the possible reference times g minus o. A guaranteed pass must meet the two-second requirement for every allowed offset. A guaranteed failure must exceed it for every allowed offset. An interval spanning a passing and a failing value supports neither guarantee. This convention does not replace the currently exact offset; it specifies how a changed assumption would be evaluated.

## C11 — Day 11, reporting scope

The incoming analyst should distinguish current observed lateness, the worst possible delay under a hypothetical uncertain offset, and the later database backlog. The report is not asked to estimate reliability for unseen samples or infer behavior on other days. S and T's shared insertion batch can be mentioned if explaining the display, but it is irrelevant to the current delivery threshold. The three seconds of calibration are a signed clock relation, not a processing delay that should be added to latency. The complete raw values remain available in the dated entries.

## C12 — Day 12, cutoff

There are no further samples, calibration changes, or amended raw timestamps. The current accepted offset remains exactly plus three seconds on the gateway clock. The complete sample set remains S, T, and U. The service threshold remains delay at most two seconds, including equality. The analyst will hand over both the factual current evaluation and enough of the conversion rule to assess a later explicit uncertainty change. Neither the unresolved display release nor the old screenshot changes the recorded sample identities or the accepted calibration.
